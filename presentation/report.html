1. Background & Problem Statement

Every login, API call, or device connection leaves a behavioural trail — timing, location, access patterns, command sequences, protocol usage. Traditional signature-based security (fixed rules, known malware hashes) fails against novel or slow, low-and-slow intrusions.

The more powerful approach is behavioural anomaly detection: learning what "normal" access looks like for a user, service account, or device, and flagging deviations — regardless of whether the target is a cloud server, an industrial edge gateway, a POS terminal, or a home IoT hub.

Problem Statement

Design and build an AI/ML system that models "normal" access and connection behaviour for users and devices, detects intrusions or compromised-credential activity in near real-time, and classifies the type of anomaly (e.g., credential misuse, lateral movement, brute force, impossible travel, device spoofing) — with an explainable risk score.

Our system handles:

  1. Sequential and behavioural data — access events over time, not static snapshots
  2. Extreme class imbalance — true intrusions are a tiny fraction of total access events
  3. Concept drift — legitimate behaviour evolves (new work patterns, new devices)
  4. Explainability — a SOC analyst needs to know why an event was flagged, not just a score
  5. Cold-start problem — how to score a brand-new user or device with no history

3. Deliverable 1 — Synthetic Data Generator

We generate 59,566 synthetic access-log events across 200 entities (150 users, 30 service accounts, 20 edge devices) spanning 30 days, with realistic per-entity behavioural profiles and injected attack patterns at a ~3% anomaly rate.

Data Schema

FieldDescription
entity_idUser or device ID (e.g., USR_001, SVC_001, DEV_001)
entity_typeuser / service_account / edge_device
timestampAccess or connection time (30-day window)
source_ip / geo_locationOrigin of the access (IP + city with lat/lon)
resource_accessedFile, endpoint, port, or device function
auth_methodpassword / token / certificate / biometric
session_durationLength of connection in seconds
action_statussuccess / failure
command_sequenceOrdered list of actions taken (e.g., login,read,write,logout)
device_fingerprintOS/firmware version, MAC address, protocol

Behavioural Profiles

Each entity is assigned a behavioural profile that includes preferred login hours, typical geo-locations (1–2 cities), a set of typical resources (3–15), preferred authentication method, average session duration, and typical command patterns. Normal events are sampled from this profile with 5% noise.

Assumptions documented: Attack patterns are generated at controlled rates (~3% total). Entity profiles are initialized with Faker-generated IPs and MAC addresses. Cities include real-world coordinates for geo-velocity calculation. The dataset is self-contained and does not require external data sources.

4. Deliverable 2 — Baseline Profiling Model

The baseline profiler learns "normal" behaviour using unsupervised methods trained exclusively on normal data:

ComponentMethodPurpose
Isolation ForestEnsemble of isolation trees (contamination=0.02)Detects global outliers by isolating data points
One-Class SVMRBF kernel (nu=0.02)Learns the boundary of normal data in feature space
StandardScalerZ-score normalizationEnsures both models operate on comparable scales

The ensemble averages both models' decision functions to produce a robust anomaly score.

Cold-Start Handling

Entities with fewer than 20 historical events are flagged with is_cold_start=1. The system handles them by: (1) using population-based baselines (global mean/std) instead of entity-specific statistics, (2) the Isolation Forest component is inherently population-based so it works without per-entity history, (3) the XGBoost downstream model learns the is_cold_start feature as a risk modifier.

5. Deliverable 3 — Detection Model

The primary detection model is a weighted ensemble combining XGBoost (gradient-boosted trees) with an LSTM Autoencoder (sequence-aware deep learning):

ComponentArchitectureRole
XGBoost Binary Classifier200 trees, max_depth=6, learning_rate=0.1, scale_pos_weight=50Primary detector — handles tabular features with class imbalance
LSTM Autoencoder2-layer LSTM (64 units), trained on normal sequences onlySequence-aware detector — high reconstruction error = anomaly
Risk Score = 0.6 × XGBoost_probability + 0.4 × Normalized_LSTM_error → scaled to [0, 100]

Class Imbalance Handling

  • scale_pos_weight=50 in XGBoost — weights the minority (anomaly) class 50× higher
  • LSTM trained on normal data only — learns normal patterns, anomalies produce high reconstruction error
  • Threshold: risk_score > 50 → flagged as anomaly

6. Deliverable 4 — Anomaly Classification

Once an event is flagged as anomalous, a separate multi-class XGBoost classifier identifies which attack category it resembles:

Attack Classes

ClassKey Discriminating Features
brute_forcefailed_auth_ratio_1h, login_burst_5min, login_count_1h
impossible_travelgeo_velocity_kmh, distance_km, time_since_last_login
credential_stuffingunique_ips_24h, failed_auth_ratio_1h, is_new_ip
lateral_movementcommand_diversity, num_commands, unique_resources_session
device_spoofingfingerprint_changed, is_new_device, auth_method_changed
low_and_slow_exfiltrationis_off_hours, session_duration_zscore, entity_age_days
insider_drifthour_deviation, entity_age_days, total_historical_events

SMOTE oversampling is applied to minority attack classes during training to ensure the classifier learns all attack types even when some are rare.

Output: predicted attack type + confidence scores (probability per class).

7. Deliverable 5 — Explainability Layer (SHAP)

We use SHAP (SHapley Additive exPlanations) TreeExplainer to provide per-alert feature attribution. For every flagged event, the system generates:

  1. Top 5 Contributing Factors — ranked by absolute SHAP contribution, with direction (increased/decreased risk)
  2. Natural Language Explanation — human-readable summary (e.g., "Flagged due to: Geo-Velocity (km/h), Failed Auth Ratio (1h), Login Burst (5min).")
  3. SHAP Summary & Waterfall Plots — visual feature attribution for global and per-event analysis

Example Explanation

"Flagged due to: Session Duration Anomaly, Avg Session Duration. Attack type: low_and_slow_exfiltration (99.99% confidence). Top contributing factors: session_duration (+7.83), entity_age_days (−0.56), is_new_ip (−0.50)."

Feature names are mapped to human-readable display names (e.g., geo_velocity_kmh → "Geo-Velocity (km/h)") for SOC analyst consumption.

Assumptions

  1. Synthetic data approximates real-world access-log distributions — validated against documented attack taxonomies
  2. Entity behavioural profiles are initialized with realistic parameters (preferred hours, locations, resources) that mimic organizational patterns
  3. Attack patterns are injected at ~3% rate, consistent with typical intrusion frequency in production systems
  4. Geo-velocity is computed using Haversine formula between consecutive login cities — assumes city-level location accuracy
  5. LSTM Autoencoder uses sliding windows of 10 events per entity — assumes sufficient event density
  6. TensorFlow is optional — system gracefully degrades to XGBoost-only if unavailable

Known Limitations

  1. Synthetic data: While carefully designed, synthetic patterns may not capture all real-world attack subtleties (e.g., sophisticated APT campaigns)
  2. Insider drift detection: The most ambiguous attack type (65% F1 on multi-class) — inherently difficult due to overlap with legitimate behaviour evolution
  3. Batch processing: Current pipeline processes data in batch mode. Production deployment would benefit from streaming integration (Kafka/Spark)
  4. Single-model explainability: SHAP explanations are computed for the XGBoost model only — LSTM contributions are not decomposed into individual feature attributions
  5. Concept drift: The system uses sliding-window features that naturally adapt, but explicit drift detection (DDM, ADWIN) is not yet implemented

12. How to Run

# Install dependencies
pip install -r requirements.txt

# Train all models (generates data, trains, evaluates, exports)
python -m ml.train_pipeline

# Launch the dashboard
python backend/app.py

# Open browser: http://localhost:5000

# Or run everything with one command:
python run.py all
